# Orcode 0.7 Design

Status: design approved in principle; written specification awaiting final user review

Date: 2026-08-22

Target: public, cross-platform npm CLI for macOS, Linux, and Windows

Chosen UI: Conversation-First Workbench

Chosen architecture: one local Node.js process with four conceptual areas

## 1. Context

Orcode 0.4.0 already provides a capable OpenRouter coding CLI: secure key storage,
balance and cost tracking, approval modes, model and compressor selection,
reasoning controls, multiple chats, multiline paste, images, reconnect, resume,
undo, voice input, an interactive TUI, and a read-only multi-model panel.

The current checkout is not a safe base for adding more autonomy without first
closing confirmed defects. In particular, the fast search path can return secret
files, several displayed OpenRouter routing settings do not reach the request,
remembered approvals often lack a match subject, run logs contain raw data, the
compressor can duplicate context, automatic verification is not wired, and the
public npm release did not complete.

This design turns the existing program into a coherent product through four
incremental releases:

- 0.4.1: correctness, privacy, routing, persistence, and distribution
- 0.5: one core and the Conversation-First Workbench
- 0.6: bounded subagent orchestration
- 0.7: provider backends, shared skills, collaboration recipes, capability
  registry, local MCP, read-only LSP, and structured Git

Each release must be usable and releasable on its own. Later releases may not
weaken an earlier security or compatibility gate.

## 2. Product goals

1. Let the user choose a suitable model from OpenRouter or a connected official
   coding-agent account while always seeing the backend, account type, active
   model, provider route, reasoning setting, role, and known cost or usage.
2. Keep conversation text dominant and make all activity observable without
   flooding the chat with raw tool or child-agent output.
3. Support safe autonomy through explicit limits, a single policy boundary, and
   verifiable completion.
4. Preserve existing chats, configuration, credentials, and the legacy
   routercode command.
5. Offer extensibility through directly shared Codex, Claude, Orcode, and
   project skills, local MCP tools, installed language servers, and hardened Git
   commands without turning Orcode into a daemon or IDE.
6. Remain installable and testable as one ordinary Node.js package on macOS,
   Linux, and Windows.
7. Let two distinct models collaborate on demand without allowing parallel
   writers, hidden fallback, or an unbounded multiplication of context and cost.

## 3. Non-goals through 0.7

- No cloud account, chat sync, hosted backend, telemetry, or plugin marketplace.
- No desktop GUI or embedded editor.
- No Orcode daemon, database, worker service, or distributed agent cluster.
- No nested subagents; only the root agent may create direct children.
- No automatic installation or download of MCP or language servers.
- No remote MCP transport, OAuth, MCP resources, prompts, sampling, or
  elicitation in 0.7.
- No LSP rename, completion edits, formatting edits, or workspace edits.
- No automatic merge, force-push, destructive Git cleanup, or force removal of
  worktrees.
- No scraping, copying, or reuse of ChatGPT or Claude browser cookies, session
  tokens, credential files, or private authentication protocols. Subscription
  access uses only the provider's documented coding-agent runtime and login.
- No silent switch between subscription allowance and pay-as-you-go API billing.
- No automatic skill activation, skill marketplace, or unattended skill install.
- No Proof, Audit Council, or Worktree Race recipe through 0.7.
- No background process that survives normal Orcode shutdown.

## 4. Compatibility contract

- Orcode is the canonical product and command.
- routercode remains a fully functional command alias through at least 1.0.
- ORCODE_* environment variables take precedence; equivalent ROUTERCODE_*
  variables remain fallbacks through at least 1.0.
- ORCODE.md is preferred; ROUTERCODE.md remains readable.
- Existing OS-keychain service names are retained so saved keys continue to
  work.
- Existing OpenRouter-only configurations continue to work without installing,
  detecting, or contacting Codex or Claude.
- Existing 0.4 chat, state, rule, run-log, and checkpoint files remain readable.
- Migrations are versioned, idempotent, validated before writing, and atomic.
- Unknown future schema versions are never overwritten with defaults.
- Neither migration nor ordinary startup silently contacts a new service.

## 5. Simplified architecture

Orcode remains one Node.js process. The four areas are conceptual module
boundaries, not services.

### 5.1 Surface

The fullscreen TUI, plain mode, JSON mode, and non-interactive prompt mode all
talk to the same OrcodeCore API. A surface sends CoreIntent values and consumes
CoreEvent values. It does not execute tools or own business state.

### 5.2 Orcode core

OrcodeCore owns the active workspace, chat, run, jobs, profiles, task tree,
approval context, and cumulative ledger. Internally it has four small concerns:

- Run: lifecycle, task scheduling, cancellation, verification, and result
- Policy: approval, stored rules, protected paths, and side-effect classification
- Models: backend accounts, role routing, context, compression, provider
  preferences, reasoning mapping, and cost or usage
- Events: ordered live updates plus redacted persistence

These are TypeScript modules in the same process. There is no IPC.

### 5.3 Capabilities

A capability is an operation available to a user, model, or both. Built-in
workspace tools, jobs, Git, LSP, MCP, Browser, and SSH share one effect
description and execute only after central policy evaluation.

The existing slash-command catalog remains the source of user commands.
CapabilityRegistry becomes the source of model tools and their TUI presenters.
Commands and model tools are related but are not forced into one abstraction.

### 5.4 Local store and external boundaries

Config, chats, permission rules, event logs, recovery journals, and worktree
metadata remain below ~/.orcode with user-only permissions. Human-readable
persistence is redacted at one storage boundary. Exact recovery artifacts are
clearly documented, retained for a bounded period, and deleted with their chat.

OpenRouter, official Codex and Claude runtimes, MCP child processes, language
servers, Git, gh, Browser, and SSH receive only the inputs explicitly prepared
for that operation. Codex and Claude own their subscription credentials; Orcode
stores only connection metadata and never reads their credential stores.

## 6. Global invariants

The following rules apply to every release:

1. A child task can never expand the root approval mode, path scope, tool set,
   step limit, or budget.
2. Every filesystem, process, network, remote, or Git-history effect is evaluated
   by the same policy layer.
3. Stored deny rules beat allow rules; protected-path always-ask rules beat both.
4. Shell permission rules match the exact command subject defined in section 7.3.
   They never use the current broad prefix behavior.
5. Model, role, configured route, resolved model/provider, reasoning, and cost
   changes are visible. No silent fallback is presented as the original route.
6. A non-mutating run may complete without verification. A mutating run reports
   complete only after its configured verification gate passes. If no gate is
   configured, it reports unverified rather than implying that tests ran.
7. One root run has one abort tree, one event sequence, one change journal, and
   one cumulative cost account.
8. Only one writer may mutate a workspace at a time.
9. A normal exit cancels models and terminates every managed child process.
10. TUI color and symbols are supplementary; all states also have text.
11. No user-visible key hint or action exists without a tested handler.
12. Orcode-owned credentials are never printed, included in command arguments,
    or passed to child processes through inherited sensitive environment
    variables. Recognized credential values in prompts or external output are
    masked before Orcode renders or persists them, except in the explicitly
    documented exact recovery artifacts from section 7.4.
13. Runtime instructions identify the product as Orcode, an independent
    multi-backend coding client, and include the configured and actually
    resolved model/backend/provider. A model may identify its actual model and
    provider, but an answer may not claim that Orcode itself was built by that
    provider or conceal an automatic route.
14. A connected account never implies permission to use it. Every run snapshots
    an explicit backend/model route, and no authentication or billing realm is
    entered by silent fallback.
15. A skill may narrow instructions, tools, paths, budget, or authority. It may
    never expand any of them, execute merely because it was suggested, or change
    the current run after its snapshot was created.
16. Collaboration is opt-in per run. Failure of a required collaborator cannot
    be presented as successful collaboration or silently continue as a
    single-model run.

## 7. Release 0.4.1: safe foundation

0.4.1 is a release blocker for all later work.

### 7.1 Canonical safe search

The built-in searcher becomes the only production search path in 0.4.1. The
current ripgrep optimization is removed rather than maintaining two security
implementations.

Requirements:

- Apply workspace containment, path policy, secret-file classification,
  .gitignore, binary detection, glob validation, and a true global result limit.
- An installed rg binary must not change behavior.
- Remove README claims that search uses optional ripgrep.
- Keep regex, fixed-string, case sensitivity, context lines, and glob behavior.

Acceptance:

- .env*, .git/**, node_modules/**, protected paths, ignored files, and binary
  files never appear.
- Existing failing workspace tests pass.
- Fixtures run with a PATH containing a fake rg and with no rg; output is equal.

### 7.2 Real OpenRouter routing

The actual main request must receive:

- the primary model and deduplicated fallback models,
- provider sort, data-collection preference, only, ignore, and fallback policy,
- the selected web behavior,
- the chosen reasoning request,
- stable cache/session identifiers.

Web search uses the current supported OpenRouter mechanism exposed by the pinned
SDK. Web is off when configured off, always present when on, and included in auto
only when the deterministic prompt classifier requests it. Any web-search cost
appears in the run ledger.

Request-capture tests assert the complete callModel payload. Helper-only tests do
not qualify. If the pinned SDK cannot express an exposed setting, Orcode must
either use a supported request path or stop exposing that setting; it may not
pretend the setting is enforced.

### 7.3 Correct remembered approvals

Every approval request contains a structured subject:

- file path or explicitly selected path glob,
- exact shell command subject from section 7.3,
- SSH host plus exact command,
- URL origin plus operation,
- MCP server plus tool and effect,
- Git repository plus exact mutation.

The confirmation UI displays the subject before offering always or never.
Remembering is disabled when no safe subject can be derived. A shell-string
subject is the exact tuple of platform, shell executable/mode, workspace-relative
cwd, and command bytes after CRLF-to-LF conversion only. Whitespace, quotes,
redirects, pipes, chains, assignments, and expansions are never parsed away or
collapsed. A structured process subject uses the resolved executable, exact argv,
cwd, and forwarded environment-variable names. Tests cover POSIX shells,
PowerShell, cmd.exe, quoting, redirection, pipes, chains, assignments, and Unicode.

### 7.4 Persistence, redaction, and retention

Create src/redaction.ts as the only source for secret detection, recursive event
redaction, transcript redaction, and export redaction. Existing pattern lists are
consolidated there.

Redacted before persistence:

- chat turns and summaries,
- exports,
- prompts and text in run logs,
- reasoning text,
- tool inputs and outputs,
- subagent messages and results.

Exact local recovery data:

- ChangeJournal may contain before/after file content needed by undo.
- Opaque SDK conversation state may contain provider context that cannot be
  structurally redacted safely.

These exact artifacts use the platform-specific PrivateStore boundary from
section 12, are never described as redacted, are bounded by retention, and are
removed with chat deletion. The README must state this plainly. RunLog.prune and
checkpoint pruning run at startup and after successful runs. A later encryption
feature is outside 0.7 scope.

### 7.5 Correct compressor state

Exactly one history source enters a main-model call:

- first run without SDK state: redacted transcript or handoff once,
- subsequent run with valid SDK state: new user request and volatile run data,
- compression run: fresh state plus handoff and unchanged current request.

The current request appears exactly once. A compression failure or cancellation
does not modify chat, summary, or committed state. The fresh state is used for
the same main call, not only after a successful answer.

### 7.6 Verification and live process output

Wire existing process callbacks through agent/core events so run_command, SSH,
Git, and verification output reaches the TUI before process exit.

After a run with ChangeJournal entries and verify mode on-edit:

1. run configured verification commands,
2. stream output,
3. on failure, permit at most the configured repair rounds,
4. apply cumulative root step and cost limits,
5. report complete only on green; otherwise unverified.

No edit means no verification is necessary. An edited run with no configured
commands becomes unverified without starting a process. Cancellation reaches the
process group and leaves no orphan.

maxRepairRounds means additional model repair runs after the initial verification.
At most 1 + maxRepairRounds verification passes and maxRepairRounds repair model
runs may occur. One pass runs configured commands in order and stops at the first
failure, so at most (1 + maxRepairRounds) times command-count child processes may
start. A nonzero test exit may start the next repair round. Spawn failure or
timeout ends unverified without a repair; cancellation ends cancelled.

### 7.7 Remaining 0.4 correctness fixes

- Harden every automatic Git invocation with disabled external helpers,
  no optional locks, no pager, and no repository-controlled process launch.
- Make chat switching rebind ChangeJournal and all chat-scoped stores.
- Make chat deletion remove transcript, lock, SDK state, run logs, checkpoints,
  and task sidecars only after one explicit confirmation.
- Invoke and test ~/.routercode to ~/.orcode migration before config/session
  access; merge safely if both exist.
- Call run-log and checkpoint retention.
- Clean browser screenshots and temporary profiles on success, error, and cancel.
- Apply configured browser path and timeout.
- Make active SSH target the default for SSH capability calls.
- Require text input/output as well as tool capability when selecting a main
  model.
- Remove embedded NUL bytes used as source sentinels.
- If a valid environment key cannot be saved because the keychain backend is
  unavailable, allow an explicit process-memory-only session rather than losing
  a valid key.
- Interactive key entry is validated and saved to the OS keychain by default.
  An environment-provided key remains process-only unless the user explicitly
  chooses key save, avoiding an unexpected copy of a managed credential.
- Startup reuses the saved key and checks authentication plus OpenRouter credit
  metadata. Only an authentication rejection invalidates it and reopens secure
  key entry. Timeout, offline, or 5xx retains the key, enters disconnected state,
  and offers reconnect. Insufficient-credit responses are distinct from an
  invalid key.
- key status, key replace, and key forget are interactive actions; replacement is
  persisted only after successful validation and forget requires confirmation.
- Read every displayed version from package.json; remove the hard-coded 0.3.

### 7.8 Packaging and 0.4.1 gate

- package.json exports both orcode and routercode bins.
- install:user creates both aliases without overwriting unrelated paths.
- Help and README show the actual supported Windows shell behavior.
- README commands are generated and checked against CommandCatalog.
- npm check, build, audit, pack, and a tarball-install smoke test pass.
- CI runs Node 22 on Linux, macOS, and Windows.
- Search security is exercised with and without an rg executable on PATH.
- Exact approval-subject tests prove that shell syntax, cwd, shell kind, argv,
  symlinks, and PowerShell never broaden a remembered rule.
- Verify tests prove the 1 + maxRepairRounds pass bound, per-pass command-process
  bound, fail-fast order, and distinguish test failure, spawn failure, timeout,
  and cancellation.
- Registry publishing is not claimed complete until npm returns the published
  version from a fresh install.
- Regression tests preserve saved-key reuse and invalid-key reprompt, explicit
  key replacement, balance status, exact model identity, reconnect, multiple-chat
  selection, bracketed multiline paste, images, voice availability behavior, and
  selectable reply suggestions. Secrets never appear in snapshots or fixtures.
- Stored-key startup, invalid-auth reprompt, offline reconnect, key replacement,
  process-only fallback, and insufficient-credit states are distinct in tests.

## 8. Release 0.5: Conversation-First Workbench

### 8.1 Core and event contract

Add:

- src/core.ts: OrcodeCore and lifecycle
- src/events.ts: versioned CoreIntent and CoreEvent
- src/jobs.ts: JobManager
- src/profiles.ts: profiles
- src/plan.ts: planning state
- src/review.ts: diff review
- src/ui/keymap.ts: one keyboard source

Existing agent, workspace, verify, browser, SSH, OpenRouter, session, and UI
modules remain adapters. cli.ts becomes bootstrap plus plain/JSON surfaces rather
than a second owner of dashboard business logic.

Every CoreEvent has version, process sequence, timestamp, scope app or run, and a
typed payload. App-scoped events cover chat, key, profile, connection, and idle-job
state and do not require run IDs. Run-scoped events additionally require runId,
taskId, optional parentTaskId, and a strictly increasing run sequence. Invalid
scope/ID combinations are rejected at the core boundary.

### 8.2 TUI layout

The accepted direction is Adaptive Workbench with conversation priority.

Fixed areas:

- One compact title row: project/chat, model plus reasoning, approval,
  connection, and session/run cost. In 0.7 the model label also exposes its
  backend/account realm when it is not OpenRouter.
- One conditional run row, visible only while active, waiting, failed, or freshly
  completed: phase, elapsed time, step, last-event age, jobs/agents, and the
  cancellation hint. Compressor, key, routing, limits, and context details stay
  in the inspector instead of permanently consuming chat space.
- Composer: one to six visual rows, real newlines, free horizontal and vertical
  cursor motion, attachments, queued-message count, and submit state.

Scrollable area:

- Conversation is the only permanently scrolling region. A focused picker or
  drawer overlay may temporarily own one bounded scroll viewport; while it does,
  conversation scrolling is frozen, and closing it restores conversation focus.
- Conversation text width is at most min(96, terminal columns minus four) cells.
- User and assistant turns get stable spacing and metadata.
- Tool, reasoning, diff, job, approval, and agent blocks are collapsed by
  default and expand in place.
- Provider reasoning text is shown only when the provider emits it. Token-only
  reasoning never invents thought text.
- Reasoning text is volatile by default and not persisted unredacted.
- Suggested replies remain selectable; ordinary typing dismisses selection and
  never blocks custom input.

Adaptive behavior:

- 120+ columns: narrow activity rail; optional inspector may be pinned.
- 80–119 columns: conversation plus overlay drawers.
- 50–79 columns: one column with prioritized compact status.
- Below 50 columns: no overflow; reduce metadata and offer plain mode, but never
  duplicate lines or corrupt input.
- Inspector is closed by default and contains model details, compressor, key
  status, limits, routing, jobs, and agents.
- With a one-row composer and no overlay, both idle and active-run snapshots leave
  at least floor(0.70 times terminal rows) rows to conversation at every tested
  size.

Interaction:

- Ctrl+P opens the global command palette.
- Slash opens the same hierarchy inline.
- Ctrl+I toggles the inspector.
- Ctrl+O opens a block navigator focused on the newest visible collapsible block;
  Up/Down selects, Enter toggles, and Escape restores the composer unchanged.
- Ctrl+T toggles reasoning.
- Ctrl+G opens agents once 0.6 is available.
- PgUp/PgDn scroll the conversation.
- Shift+Enter inserts a newline; Alt+Enter is the documented fallback when a
  terminal does not distinguish Shift+Enter. Up/Down moves vertically inside
  multiline input before falling back to history navigation.

All hints and handlers come from src/ui/keymap.ts. Tests reject orphan hints,
orphan handlers, cell-width overflow, duplicated resize output, or cursor
positions based only on Unicode code points instead of terminal cells.

### 8.3 Hierarchical command catalog

CommandCatalog becomes declarative and recursive. Each entry defines aliases,
description, subcommands, argument kind, picker, current value renderer, and
handler identifier.

At minimum, these are fully interactive:

- model, models, allow, chat, compress, think, verify, provider, fallback,
- key, image, ssh, profile, jobs, plan, review,
- agents in 0.6,
- collab, cross, skill, skills, tools, mcp, code, git, worktree, and pr in 0.7.

Typing filters the current level. Arrows select, Tab completes, Enter applies,
and Escape closes without modifying the draft. Help, README generation,
dispatch, and palette are invariant-tested against the same catalog.

model and models open the same searchable picker. A result row shows model ID,
input/output price, context, and text/tool/reasoning/image support; detail shows
provider routing and availability. Typing K filters immediately and arrows never
move the conversation while the picker is focused. compress exposes status,
mode, now, reset, and model as real child entries; compress model opens the same
picker in compressor-role mode. think exposes only supported effort/budget
choices, shows the requested and provider-mapped value, and keeps the active
choice visible in the title row or inspector. Command and alias matching use
whole tokens, so allow can never dispatch approve accidentally.

In 0.7 the canonical provider subtree is exactly `setup`, `connect`, `enable`,
`disable`, `reconnect`, `status`, `models`, and `logout`; `disconnect` is a
dispatchable alias of `disable` and has no duplicate palette row. `collab` is the
one canonical collaboration tree;
its `cross` node owns `run`, `models`, `swap`, `status`, and `stop`. `/cross ...`
is a prefix alias that maps token-for-token to `/collab cross ...`, so palette,
help, completion, and dispatch derive from one subtree and never disagree.
`skill` is likewise the canonical shared catalog and `skills` its alias; their
child entries are list, show, use, clear, refresh, and sources. Aliases remain
dispatchable and discoverable in detail text but do not duplicate palette rows.

### 8.4 Live and background jobs

JobManager owns every shell-like child process.

- Foreground operations stream output and await completion.
- run_command with background true and the direct user command job start --
  COMMAND start a background job and return a job ID immediately. The approval
  shows command, cwd, and background lifetime; remembered permission uses the
  same exact subject as the foreground form.
- Jobs expose status, command, cwd, duration, exit code, and bounded stdout and
  stderr ring buffers.
- User commands: jobs list, job show, job focus, job stop, job stop-all.
- Model capabilities may inspect and stop jobs. Starting a job still requires
  the normal shell approval.
- Introduce WorkspaceWriterLease in 0.5. Every foreground or background shell
  process holds it for its entire lifetime because Orcode cannot prove an
  arbitrary command read-only. Agent edits and other workspace mutations wait;
  chat input and job inspection remain interactive.
- Jobs are children of the current Orcode process and deliberately do not
  survive restart.
- On exit: graceful terminate, short deadline, then force terminate.

### 8.5 Plan and review

Plan is a technical execution mode, not a prompt suggestion. It allows built-in
read/search and hardened read-only Git capabilities, but blocks file writes,
shell, SSH, external writes, and mutating plugins. The resulting PlanBlock may be
edited, discarded, or approved. Approval starts a normal act run with the exact
plan in context.

Review uses ChangeJournal and the existing diff renderer. It supports file and
hunk navigation, accept, reject, skip, accept all, and reject all. Multiple
journal entries for one file first collapse to first before and final after.
Decisions are collected per file, the current file is compared once with that
final after-state, and all rejected hunks are applied as one atomic combined
patch. A mismatch creates a conflict and writes nothing. Accept is a decision
only. Undo remains the full-run fallback.

### 8.6 Profiles

Built-in profiles adjust safe behavior but never contain credentials:

- safe: read-only, web off, verify on
- fast: low reasoning, six steps, compressor auto
- code: high reasoning, ask approvals, verify on
- autonomous: allow-all plus verify, with mandatory activation warning; it uses
  min(current configured limit, 12 steps) and min(current configured limit,
  USD 1.00) per root run, supplying those defaults when absent, and may never
  raise a user's stricter limit

Applying a profile is session-scoped. profile save persists a named profile
under ~/.orcode only after showing an exact configuration diff. Custom profiles
may reference model roles; built-in profiles do not silently change the user's
main model.

### 8.7 0.5 acceptance gate

- All 0.4.1 gates remain green.
- Full PTY tests cover 40x20, 50x20, 80x24, 120x35, and 160x40.
- No-overlay idle and active-run snapshots assert the exact conversation width
  formula and 70-percent row floor. An overlay may cover conversation rows and
  own one temporary, exclusively focused scroll viewport. Escape closes it to
  the byte-identical composer/draft state; no overlay may overflow, duplicate
  fixed content, scroll simultaneously with conversation, or become permanent.
- Five resize cycles never duplicate a fixed or scrolling line.
- Emoji, combining characters, and CJK input preserve cell widths and cursor.
- Multiline paste is one draft and one later submit, including while busy.
- A pasted multiline draft plus an image is submitted as one multimodal turn;
  image removal never alters the draft.
- Suggested replies are keyboard-selectable, while ordinary typing immediately
  returns to unrestricted custom input.
- Live output appears before process completion.
- A background job runs while the user edits a multiline draft and is cleaned
  on exit.
- A background job prevents every workspace edit until it exits or is stopped;
  its writer lease is then released exactly once.
- Plan mode cannot mutate the workspace.
- Two rejected hunks in one file apply together; hunk rejection cannot overwrite
  external changes.
- Real 0.4 fixtures migrate without data loss.
- Command-catalog and keymap invariants are green.
- App/run event scope and ID validation, block navigation, Alt+Enter fallback,
  and autonomous 12-step/USD-1.00 ceilings are covered.

## 9. Release 0.6: bounded agent orchestration

### 9.1 Scope

One root agent may start direct children with roles explore, implement, or
review. Compressor and verifier also adopt the common worker lifecycle.

Limits:

- one process and one workspace,
- no grandchildren,
- default maxParallel 3, allowed range 1–8,
- default maxTasksPerRun 8,
- at most one implement child,
- read/review children may run concurrently,
- no shell, SSH, Browser, MCP, or arbitrary external-network capability for
  model-based children; only the verifier may execute exact user-configured
  local commands,
- no child remains active after root termination.

Panel remains a separate tool-free model comparison.

### 9.2 Modules and worker contract

Add:

- src/orchestration.ts: AgentSupervisor, scheduler, tree, messages, cancellation
- src/workers.ts: common Worker contract and adapters
- src/agent-tools.ts: root-only agent control tools

WorkerContext contains task descriptor, AbortSignal, approval ceiling, reserved
budget, capability snapshot, emit, spawn, wait, send, and cancel. WorkerResult
contains outcome, summary, changed files, verification, cost, configured and
resolved model, stale flag, and redacted error.

Main, explore, implement, and review use one extracted ModelWorker. Role,
instructions, route, capability scope, approval ceiling, steps, and cost are
configuration, not separate agent implementations. Verifier and compressor use
the same lifecycle without the coding loop.

### 9.3 Task tree and scheduler

States:

- queued, running, waiting-approval, waiting-child,
- cancelling,
- completed, unverified, partial, failed, cancelled, interrupted.

Terminal states are immutable and produce one terminal event and one result.
The root may finish only when every required child is terminal and its verification
decision is terminal. Final assistant text is neither rendered as final nor
persisted before this barrier. If the model attempts to finish with unconsumed
required results, the supervisor waits and gives their compact results to one
normal, budgeted main-model continuation. If that continuation cannot run, the
provisional text is labeled partial and never complete.

maxParallel counts non-root workers that currently own an execution slot: child
agents, compressor, and verifier. The root and background jobs do not count.
Queued tasks own no slot. waiting-child and a waiting-approval state with no
active model/process release their slot; a supposedly waiting task may not release
until its active operation is stopped. A global writer lease covers root and
implement-child mutations. Each child has its own ReadRegistry; all writes share
the root run ID and ChangeJournal so undo reverses the whole user run. Read-only
findings become stale if the workspace changes before result use.

### 9.4 Approval and budget inheritance

Effective child authority is the intersection of:

- root approval mode,
- role ceiling,
- spawn path scope,
- central policy.

Explore is read/search only. Review adds diff and diagnostics. Implement adds the
built-in edit tools within its path scope but no shell. Verifier may run only
exact configured commands. Compressor has model access only. Omitting spawn paths
means the workspace root excluding protected paths; supplied paths may only
narrow it. All reads and writes resolve real paths and reject symlink escape.
Role and path ceilings are evaluated before remembered allows.

Each root run owns RunBudgetAccount. Main calls, finalization, compressor, repair,
and every child all reserve from the same monetary ceiling before a model request
when the route exposes a monetary estimate. Every worker also reserves bounded
turns, steps, and time. Spawn atomically reserves its known currency and task
ceilings; parallel reservations cannot exceed the unreserved remainder. A
terminal task or cancelled request releases unused reservation only after its
operation drains. Known actual cost, including a late provider report after
cancellation, is charged exactly once to the original root. A 0.7 subscription
route whose currency is unavailable follows the explicit preflight contract in
section 10.1 and is never recorded as zero cost. Crash recovery closes stale
reservations and preserves known charges before any new spend. Workspace
daily/total monetary budget remains the outer boundary for known currency.
Provider-reported cost can arrive after a response, so the TUI describes the
limit honestly rather than promising zero overshoot.

### 9.5 Role-based model routing

The root requests a role, never an arbitrary child model. ModelRouter maps main,
compressor, explore, implement, and review to user-visible role settings with
the configured fallback chain.

Through 0.6 these routes resolve inside OpenRouter. The 0.7 BackendRegistry
extends the resolved route with backend and account realm without changing the
role contract or allowing a child to choose a billing realm.

Before a child starts, Orcode checks required modalities, tools, context, and
reasoning support. Every route event shows role, configured model, resolved
model/provider, reason, and task budget.

### 9.7 Conversation-first agent UI

Normal chat shows only child start, approval, meaningful error, and completion
as compact blocks. Full child transcript, reasoning, and tool output remain in
the agent drawer.

Ctrl+G or agents opens a drawer. At 120+ columns it may occupy the optional right
inspector; below that it is a full overlay. Each row shows stable short ID, role,
state text, model, current phase/tool, elapsed time, and cost. Detail shows path
scope, approval ceiling, limits, latest event, output, and result.

There is exactly one animated spinner in the whole frame.

### 9.8 Persistence and recovery

One root run retains one ordered NDJSON event file. Each envelope includes
version, sequence, root run, task, parent task, timestamp, and redacted payload.
Child transcripts are not normal root chat turns. Root prompt and final answer
remain the chat contract.

After crash, nonterminal tasks become interrupted. An interrupted worker is never
continued. Orcode never automatically replays a model or side effect. Recovery
offers: start a new root referencing completed child results and current workspace
state; undo all journaled changes; or keep current changes and close the recovery
record after confirmation. Truncated events replay only through the last valid
envelope. Stale reservations close before the new root begins.

Cancellation has a five-second drain deadline before managed child processes are
force-terminated. Queued tasks cancel immediately; open approvals are closed as
denied; waits reject; writer leases and budget reservations release only after
the related operation drains. Late provider cost remains chargeable once.

### 9.9 0.6 acceptance gate

- Common lifecycle tests cover main, child, verifier, and compressor.
- Twenty fake tasks never exceed concurrency.
- Two writers never overlap.
- Root read-only always blocks child edits.
- always-ask remains effective under child allow-all.
- Path escape, symlink escape, shell, SSH, and network capabilities remain blocked
  for children even under root allow-all and remembered allows.
- Main, finalization, compressor, repairs, and children together never reserve
  beyond the root; cancellation/crash releases unused reservation and late cost
  is charged once.
- Costs and terminal events are recorded exactly once.
- Wait any/all, messages, partial failure, child cancel, and root cancel work.
- Root cancellation leaves no model, verify, or shell operation.
- Queued cancellation, open approval, wait, writer lease, noncooperative process,
  and late-cost cancellation paths all terminate within their defined boundary.
- Undo covers child changes.
- Truncated-event crash reconstruction never re-executes an effect and resumes as
  a new root only.
- Final assistant text cannot become complete or persistent before required-child
  and verification barriers.
- PTY snapshots prove chat dominance and stable drawers at 80, 120, and 160
  columns.

## 10. Release 0.7: extensible capabilities

### 10.1 Model backends, accounts, and setup

Add `src/backends.ts` for the registry and contracts,
`src/backend-codex.ts` and `src/backend-claude.ts` for managed-agent adapters,
and `src/patch-proposal.ts` for validation and central application. Existing
`src/openrouter.ts` implements the raw-model adapter.

BackendRegistry separates a model backend from a connected account and from a
model route. A backend declares:

- stable backend ID and kind: raw-model or managed-agent,
- credential owner and documented login mechanism,
- availability and version probe,
- model discovery and canonical model identity,
- modalities, tool and reasoning capabilities,
- usage meter: exact currency, provider allowance, or unknown,
- reasoning mapper and Worker factory.

The built-in backends are:

1. **OpenRouter** remains the stable raw-model backend. Orcode owns its API key
   in the OS keychain, validates authentication and credit, uses the existing
   tool loop, and records provider-reported dollar cost.
2. **ChatGPT subscription Preview** uses an installed, allowlisted official
   `codex app-server` over local stdio. Login uses its browser or device-code
   flow. Because the installed Codex CLI still labels app-server experimental at
   design time, this backend is visibly Preview, disabled until explicitly
   selected, and never advertised as stable in 0.7. Orcode does not opt into
   experimental app-server fields or externally managed token modes.
3. **Claude subscription Preview** uses an installed, allowlisted official Claude
   Code or Claude Agent SDK runtime. This backend is visibly Preview and
   policy-dependent because subscription eligibility for Agent SDK, print mode,
   third-party use, and paid overage may change. A failed eligibility or billing
   probe makes the route unavailable.

Both subscription runtimes own and refresh their credentials. Orcode never
opens, parses, copies, exports, backs up, or places those credentials in argv.
Preview promotion requires a stable provider contract plus all existing
conformance and live gates; passing local tests alone does not relabel an
experimental upstream interface as stable.

Managed-agent backends never receive the live workspace path. Before launch,
Orcode materializes a PreparedWorkspaceView from CanonicalSafeSearch into a
private temporary root. It contains only in-scope regular files, safe project
instructions, and explicit attachments; ignores protected paths, links, sockets,
devices, VCS internals, dependency trees, and recognized secrets; and records a
manifest of relative path, source hash, copied hash, size, omissions, and root
revision. Default limits are 20,000 files, 64 MiB total, and 2 MiB per file;
configurable maxima are 100,000 files, 256 MiB total, and 8 MiB per file. Hitting
a limit is visible and never silently changes a complete scan into a complete
claim.

ManagedRuntimeSandbox is a normative OS-enforced boundary around that view. It
allows filesystem reads only from the immutable view and required runtime
libraries, writes only to a dedicated private scratch/auth area, and no access
to the live workspace or unrelated user files. Agent tools have no external
network; runtime network is restricted to documented provider authentication and
model transport. Provider-internal read/search subprocesses may run only inside
the sandbox and its dedicated POSIX process group or Windows Job Object. Hooks,
plugins, MCP, background terminals, auto-update, inherited API/bearer-key
variables, and unsandboxed child execution are disabled. Launch uses shell false,
explicit executable and argv, a scrubbed environment, finite resources, and the
runtime's bare or minimal configuration. If this boundary cannot be enforced for
the exact platform/runtime version, the backend is unavailable, not merely
reviewer-only.

Managed workers return text, structured findings, or a validated PatchProposal.
When one is the lead, Orcode applies its proposal through the central transaction
path under WorkspaceWriterLease and then returns the resulting diff for another
model pass. The runtime itself never writes the live workspace.

Provider-owned local transcripts are a separate persistence boundary and may not
silently bypass Orcode redaction. The Claude adapter requires documented
no-session-persistence mode. The Codex adapter sends task content only through a
documented ephemeral thread; if the supported app-server provides only
ephemeral forks, it creates a content-free base, forks before sending task or
project content, and deletes the empty base at terminal. Credential refresh and
provider-owned credential metadata are permitted in the dedicated auth area, but
task text, tool output, reasoning, and patches may not enter documented
provider-owned local task-history paths inside the adapter-declared runtime home
under the default policy. This local claim does not cover provider cloud
retention or undocumented server behavior; setup links and summarizes the active
account policy. A runtime lacking nonpersistent execution plus an isolatable,
inspectable local history root is unavailable until the user explicitly enables
a separately documented provider-history policy.

A PatchProposal is versioned data, not permission. It contains proposal ID,
source run and task, base workspace revision, bounded workspace-relative regular
file create/update/rename/delete operations, and expected preimage hashes.
Canonical source and destination sets must be unique after platform case-folding;
links, hard-linked targets, path aliases, rename cycles, protected paths, and
overlapping operations are rejected. The complete proposal and every hash are
revalidated immediately before commit, after central policy and approval.

Patch application uses a durable WorkspaceTransactionManifest in PrivateStore
and a declared, user-only staging/stash root on the workspace filesystem. This
reserved root is protected from model access, search, Git operations, and normal
workspace presentation. After-content and all preimages are staged and fsynced
before the manifest enters `prepared`. Deletes move to stash; each replace/rename
advances an idempotent manifest phase; new parent directories are recorded for
rollback; completion fsyncs the workspace and ChangeJournal before marking
`committed`. Validation or approval failure creates no transaction artifact.
Staging or any pre-commit failure changes no target/user file; it may leave only
declared private transaction artifacts, which startup recovery cleans or resumes.
A process or I/O interruption after commit begins marks the workspace
recovery-required: before any new use, Orcode idempotently rolls back an
`applying` transaction or verifies and finalizes a fully `committed` one. If
outside changes prevent safe recovery, all runs remain blocked with exact manual
recovery paths. Patch repair is a visible, budgeted model turn; Orcode never
guesses how to repair malformed output.

First-run setup is a multi-select, not a three-provider requirement:

- Use OpenRouter
- Connect ChatGPT through Codex (Preview)
- Connect Claude through Claude Code (Preview)
- Configure another provider later

The user may select one or more. Setup may run a scrubbed, time-limited
`--version` probe, but it performs no login, account refresh, or backend session
until the user selects connect. It explains maturity, account realm, provider
history, and possible paid overage before login and lets unavailable choices be
skipped. At least one backend must be usable before an online run; an existing
OpenRouter configuration performs no new probe or contact until the user opens
`provider setup`. Setup may configure preferred collaboration roles but never
turns collaboration on globally.

Canonical commands:

- provider setup
- provider connect BACKEND
- provider enable BACKEND
- provider disable BACKEND
- provider reconnect BACKEND
- provider status
- provider models BACKEND
- provider logout BACKEND

Alias:

- provider disconnect BACKEND -> provider disable BACKEND

`key` continues to manage only explicit API-key backends. disconnect is an alias
for disable: it changes only Orcode route metadata and never touches the shared
provider credential store or another client. reconnect is transport/health only
and never starts login, logout, or a model turn. logout is separate,
always-ask/no-remember, requires an idle and fully drained backend, and displays
whether the official action affects only an Orcode-dedicated provider home or a
globally shared Codex/Claude login. Orcode never deletes a foreign credential
file directly. Provider status is one of available, login-required,
limit-reached, incompatible-runtime, policy-unavailable, offline, or disabled
and always has a next action.

A route is backend plus a locally assigned account alias, opaque account
fingerprint, billing realm, and canonical model. The fingerprint is either a
keyed local HMAC of a documented opaque realm identifier held only transiently,
or a locally generated realm ID when the provider exposes no safe identifier; it
is never an email, raw account ID, or profile field. Fallback may cross a backend,
account fingerprint, or billing realm only when the user explicitly configured
that exact transition. Before sending task content, every managed runtime must
report the expected auth mode and realm; a mismatch drains it and fails closed.

OpenRouter pay-as-you-go, ChatGPT subscription with provider-managed credit
behavior, Claude subscription with provider-managed usage-credit behavior, and
any explicit API key are separate realms. All OpenAI, Anthropic, Bedrock, Vertex,
and gateway API-key/token environment variables are scrubbed from subscription
workers. Orcode uses the label `plan-only` only when an official control can
enforce no paid overage. Otherwise setup and every unsaved preflight say that the
provider may draw purchased or usage credits after plan allowance, and the route
is labeled `subscription-provider-managed-overage`; it never silently becomes an
API route.

Cross requires two distinct canonical model identities after route resolution;
two routes to the same model family produce a warning and are not accepted as
two different models unless the user makes an explicit advanced override. Two
different OpenRouter models are valid; OpenRouter plus a subscription model is
valid; ChatGPT plus Claude is valid. Connecting all three is never required.

RunBudgetAccount contains a MoneyLedger and PlanUsageLedger. Known currency is
reserved and charged exactly once. Provider allowance, reset window, and limit
state are displayed and atomically reserved locally when exposed. Unknown plan
usage is labeled `plan usage, dollar cost unavailable`, never `$0.00`, and is
bounded by root-wide worker-start, turn, input-token, output-token, and wall-time
ceilings. Parallel starts reserve from the same ledgers; a changed or exhausted
provider limit stops the next call and late usage settles once after drain.

For every unknown-currency route, including an ordinary non-collaboration run,
default root ceilings are eight worker starts, 24 model turns, 512K input tokens,
64K output tokens, and 30 minutes wall time. Configurable hard maxima through 0.7
are 16 worker starts, 64 turns, 2M input tokens, 256K output tokens, and two hours.
The existing stricter step, task, recipe, context, output, or workspace limit
wins. Input is reserved before send; provider maximum-output parameters reserve
the remaining output allowance; a call that cannot fit does not start.

Unknown-usage consent is not inherited from allow-all or a model fallback. A
remembered consent subject is exactly backend, opaque account fingerprint,
billing realm, canonical model, recipe, role count, and all root limits. It is
session-only by default, may be persisted for at most 30 days with an explicit
expiry, and is invalidated by any subject, limit, account, or provider-policy
change.

Every provider request has a stable operationId and durable state machine:
prepared, sent, acknowledged when the protocol provides an acknowledgement,
streaming, terminal, or indeterminate. Automatic retry is permitted only from
prepared after the transport proves that no task bytes were accepted and no
provider worker started. Once task bytes may have been accepted, a disconnect,
crash, or missing terminal event becomes indeterminate unless the exact tested
provider version offers an official idempotency key or status/reattach contract.
Reconnect may query or reattach to that same operation; it never resends task
content or creates a replacement operation. Every terminal result and late usage
report is deduplicated by operationId.

Before replace, single-model continuation, or handoff, Orcode drains the old
operation and its complete POSIX process group or Windows Job Object, force-kills
it after the shared cancellation deadline, records any late terminal event, and
settles both ledgers. If acceptance remains unknown, the source stays
indeterminate and is never resumed or replayed. A new worker gets a new
operationId and an explicit reviewed continuation bundle.

### 10.2 Directly shared skills

Add `src/skills.ts` for discovery, source identities, local matching, activation,
and immutable SkillBundle creation. It does not execute tools.

SkillRegistry discovers compatible `SKILL.md` packages directly instead of
copying them. Default user roots are `~/.orcode/skills`, the configured Codex
skills root (normally `~/.codex/skills`), and the configured Claude skills root
(normally `~/.claude/skills`). Equivalent `.orcode/skills`, `.codex/skills`, and
`.claude/skills` directories inside the active workspace are project roots.
Additional roots require explicit configuration.

Orcode treats every skill root as untrusted, read-only supply-chain input. It
never edits, removes, or installs into Codex or Claude roots. Missing roots are
ignored. Directory enumeration uses lstat; before every discovery read Orcode
resolves the candidate and parent real paths, rejects links or root escape, opens
without following links where the platform permits, and verifies identity again
after read. Every discovered skill has a stable source-qualified ID containing
origin, scope, and declared name, so same-name skills remain separate instead of
silently shadowing one another. The picker always displays source and scope.

Discovery reads only bounded frontmatter needed for name, description, and
compatibility. The default frontmatter read limit is 32 KiB and its immutable
hard maximum is 64 KiB; a missing terminator within the limit rejects the entry.
A local deterministic matcher ranks those fields against the draft and may show
a compact suggestion row above the composer. Draft text does not leave the
process merely to generate suggestions. Suggestions never activate a skill. Tab
focuses the row, arrows select, Space toggles, Enter applies the selection and
returns focus to the unchanged draft, and ordinary typing keeps custom input
unrestricted. `skill use NAME` is the explicit command equivalent; on a collision
it requires the source-qualified ID.

Composer states make the Tab behavior exclusive. When the first non-whitespace
draft token is `/`, inline-command mode suppresses skill suggestions and Tab
completes the selected command. In ordinary prose mode, a visible skill row owns
Tab; once focused, arrows, Space, Enter, and Escape act only on that row. Closing
either state restores the exact draft and cursor.

Selections belong to the current draft and next submitted run, not a global
mode. Submission consumes the selection only after PreparedSubmission validates
routes, attachments, every selected skill hash and trust decision, recipe, and
budget, and immediately before RunStart is committed. Rejection, changed hashes,
invalid resources, or any other preflight failure starts no run, reserves no
budget, and restores the exact draft bytes, cursor, attachments, and armed
selection. A later successful task has fresh suggestions unless the user selects
a skill again. `skill clear` removes the armed selection without changing the
draft.

Activation repeats the safe-open checks, reads the full `SKILL.md`, resolves a
bounded instruction/resource graph, and materializes every referenced resource
with real path, size, content hash, and bytes into an immutable private snapshot.
Any identity or hash change during materialization fails stale. One bounded
SkillBrief per selected skill records source, instructions, immutable resources,
and requested capabilities; their ordered SkillBundle has its own content hash.
Later resource loads use only this snapshot, never the mutable foreign root. A
source change invalidates the catalog for the next run but cannot alter a running
task. Codex, Claude, OpenRouter, Lead, and Challenger receive only the same
serialized SkillBundle in 0.7; backend-native skill discovery or path invocation
is disabled because equivalence and script suppression cannot be guaranteed.

Default activation limits are four selected skills, a 256 KiB `SKILL.md`, graph
depth four, 64 resources and 4 MiB resource bytes per skill, 1 MiB per resource,
a 4 MiB serialized SkillBrief, and an 8 MiB SkillBundle. Immutable hard maxima
through 0.7 are eight selected skills, a 1 MiB `SKILL.md`, depth eight, 256
resources and 16 MiB resource bytes per skill, 2 MiB per resource, a 16 MiB
SkillBrief, and a 32 MiB SkillBundle. Limits apply during safe-open reads; an
overflow invalidates the whole selected skill or bundle and never yields a
partial activation.

Unknown metadata is displayed but has no authority. A skill's requested tools,
paths, scripts, network, or budget can only be intersected with existing policy.
Referenced resources must remain under the skill root and are size-limited,
secret-scanned, redacted, and stored as data in the immutable snapshot. Scripts
never run during discovery, suggestion, activation, or provider-native loading.
A later model request to execute a snapshotted script becomes an ordinary exact
capability request and approval. First activation of every previously unapproved
skill content hash, including user-wide Codex and Claude sources, previews its
source, instructions, resource manifest, and requested capabilities. Changing
any instruction or resource hash invalidates the prior confirmation.

Commands:

- skill list [QUERY]
- skill show SOURCE:NAME
- skill use SOURCE:NAME
- skill clear [SOURCE:NAME]
- skill refresh
- skill sources

The title row shows only an active-skill count when space permits. Names and
hashes live in the inspector and run preflight. There is no skill marketplace,
automatic install, automatic activation, or model-initiated installation in
0.7.

### 10.3 On-demand collaboration recipes

Add `src/collaboration.ts` for recipe definitions, preflight, ContextPacket and
HandoffBundle construction, and presentation state. Execution remains in the
existing AgentSupervisor and Worker contracts.

Collaboration recipes are declarative TaskGraph templates over the 0.6
AgentSupervisor, not a second agent system. A recipe declares its worker roles,
dependencies, context policy, writer policy, completion gates, default limits,
and UI summary. All workers share the root abort tree, policy ceiling, ledger,
event sequence, and WorkspaceWriterLease.

Before dispatch, Orcode creates one versioned ContextPacket from the current
request, relevant chat state, project instructions, selected SkillBundle, and
workspace references. Existing compression rules still guarantee that the
current request appears exactly once. If the configured compressor is used, its
configured and resolved backend/model, duration, and known usage are visible and
charged to the same run. Cross receives byte-identical Orcode ContextPacket
payloads and hashes. Provider-owned system prompts, account policy, safety
layers, and runtime metadata remain outside that packet, so Orcode does not claim
that two providers have identical hidden execution context. Scout may derive
explicitly path-scoped child packets whose source hash remains visible.

CollaborationPlan makes every content bound finite and visible. Defaults are an
8 MiB serialized ContextPacket, 128K cumulative input tokens and 16K cumulative
output tokens per worker, and 384K input plus 64K output tokens for the whole
collaboration root. Configurable hard maxima through 0.7 are 32 MiB, 1M input and
64K output per worker, and 2M input plus 256K output per root, always further
limited by the resolved model. HandoffBundle defaults to 512 KiB and has a 2 MiB
hard maximum. Reservations use an official tokenizer when available and a
documented conservative estimate otherwise, then settle against emitted usage.
The current request is never silently truncated: compression or deterministic
omission records what changed, and an irreducible oversize task fails preflight
with the exact limit.

Collaboration is off by default and selected per run. `collab` opens one compact
picker. The canonical Cross subtree is `collab cross run|models|swap|status|stop`;
`cross` is only its token-for-token prefix alias. Bare `collab cross` and bare
`cross` open the same Cross preflight. If the composer already contains a draft,
opening or cancelling the picker preserves it exactly. The preflight shows every
role's configured and resolved backend/model, canonical identity, reasoning
setting, active skills, context scope, authority, maximum turns, content limits,
known currency, unknown plan usage, and total limits.

The recursive command catalog exposes descriptions for `collab cross`, `collab
scout`, `collab debug`, `collab handoff`, `collab status`, and `collab stop`.
Cross children exist only below the canonical `collab cross` node; completion of
`cross` reuses those exact child nodes and handler IDs. From Ctrl+P, `collab cross
run` applies to the separately preserved prose draft. When typed as a slash
command, text after `collab cross run` or its `/cross run` alias is the task; with
neither form of task it returns focus to the composer and arms only the next
submission. An armed recipe is consumed once and then returns to ordinary work.
Route changes while a run is active apply only to a later run. status and stop
act immediately instead of joining the queued chat-input path.

The 0.7 recipes are:

**Cross -- Lead plus Challenger**

1. Lead and Challenger independently analyze the same immutable, redacted Orcode
   ContextPacket bytes and SkillBundle hash; provider-owned hidden context may
   differ as disclosed above.
2. The Lead creates the plan. The Challenger returns explicit critique.
3. The Lead revises and is the only logical implementer. Raw-model leads may use
   the normal edit loop; managed-agent leads return PatchProposal values for
   central application as defined in section 10.1.
4. Verification runs once the lead changes are stable. The Challenger receives
   the task, accepted plan, final diff, changed-file excerpts, and verification
   result, not the complete raw chat or private reasoning.
5. A blocking post-change finding may trigger at most the preflight-disclosed
   Cross repair limit, default one. The Lead repairs, verification reruns, and
   the Challenger rechecks. An exhausted limit or persistent blocker ends
   partial or blocked, not complete. The Lead produces one unified final answer
   only after every required node and verification gate is terminal. For a
   non-mutating task the Challenger reviews the proposed answer instead of a
   diff.

**Scout**

The supervisor divides a large or unfamiliar repository question into two to
four read-only, path-scoped investigations. Scouts may run in parallel and
return compact findings with file references and confidence. The Lead discards
stale findings after workspace changes, synthesizes the result, and remains the
only possible writer if the task proceeds to implementation.

**Debug**

Two read-only diagnosticians create independent, falsifiable hypotheses. The
Lead selects the smallest discriminating checks; only Verifier executes exact
user-configured commands. A repair begins only after a failure is reproduced or
the UI explicitly labels the diagnosis unconfirmed. The Lead alone proposes or
applies the fix, and the normal verification gate must prove the result.

**Handoff**

Handoff is sequential rather than parallel. Orcode creates a versioned,
redacted, size-bounded HandoffBundle containing bundle ID, source run/task and
operation ID/state, last included event sequence, workspace revision and diff
hash, ordered SkillBundle hashes, source and destination routes, the task,
accepted decisions, relevant file references, completed verification, completed
effects, known costs or usage, omissions, and unresolved work. Raw reasoning,
credentials, unbounded transcripts, incomplete tool calls, and uncertain
external effects are excluded; an indeterminate source is represented only as a
typed warning and is never assumed complete.

The user selects the destination and reviews the exact serialized bundle. Review
freezes its bytes and hash. Immediately before dispatch, Orcode revalidates the
source operation state, event sequence, workspace/diff revision, SkillBundle,
and destination route. Any change marks the bundle stale and returns to a newly
generated preview without reserving or sending. A successful dispatch creates a
new operationId. A failed worker or reconnect never causes automatic replay; the
UI offers reconnect, choose model, explicit handoff, or explicit single-model
continuation.

Panel remains the tool-free answer comparison. Plan, Review, Verify, profiles,
and direct child agents retain their existing meanings and are not duplicated as
new collaboration recipes. Proof, Audit Council, arbitrary nested teams, and
Worktree Race are deferred.

During collaboration the conditional run row shows recipe, phase, Lead state,
Challenger or worker count, last-event age, and combined known usage. There is
one spinner for the whole frame. The conversation contains one collapsible
CollaborationBlock with explicit plans, critiques, evidence, decisions, routes,
and per-worker usage. It never fabricates hidden thought text. Full operational
details live in the agent drawer, while the final answer stays the dominant
conversation content.

Required-worker failure produces partial or failed, never complete. The recovery
actions are reconnect, replace the failed route, or continue singly after an
explicit user decision. Replace and single continuation start a new budgeted
worker from a reviewed HandoffBundle; they do not resume or replay an unknown
operation. Cancel drains every worker and provider runtime through the shared
abort tree.

### 10.4 Capability registry

CapabilityRegistry is the single model-tool source. A capability declares:

- stable ID and model-visible name,
- origin: builtin, mcp, lsp, or git,
- exposure: model, user, or both,
- title, description, validated input/output schema,
- deterministic list of effects and subjects,
- executor and TUI presenter.

Effects include workspace-read, secret-read, workspace-write, local-process,
external-read, external-write, git-history-write, protected-delete, and
unclassified.

Central policy uses this minimum matrix after path policy and stored deny rules:

| Effect | read-only | ask | auto-edit | allow-all |
| --- | --- | --- | --- | --- |
| workspace-read | allow | allow | allow | allow |
| workspace-write | deny | ask | allow | allow |
| local-process or external-read | deny | ask | ask | allow |
| external-write | deny | ask | ask | allow |
| git-history-write | deny | always ask | always ask | always ask |
| secret-read or protected-delete | deny | always ask | always ask | always ask |
| unclassified | deny | ask, no remember | ask, no remember | ask, no remember |

An explicitly unsupported or hard-disabled operation is always denied. Remembered
deny rules are applied first. For multiple effects, the strictest decision wins:
deny, then always-ask/no-remember, then ordinary ask, then allow. A remembered
allow may skip only an ordinary ask for the same exact subject; it can never skip
deny, always-ask, no-remember, role/path policy, or another effect's decision.
MCP annotations cannot lower effects; an unclassified dynamic MCP tool starts as
unclassified plus external-write until the user stores a stricter local
classification.

The registry is snapshotted at run start. Dynamic MCP changes apply on the next
run, not midway through a tool loop. Names and collision suffixes are stable.
One invalid dynamic tool does not disable unrelated capabilities.

### 10.5 MCP client

Orcode 0.7 is an MCP host/client for explicitly configured local stdio servers.
It supports tools and workspace roots only.

It does not support Streamable HTTP, OAuth, resources, prompts, sampling, or
elicitation in this release. The implementation plan records one concrete
production-stable official TypeScript SDK version in package.json and the lockfile
before coding starts; main branches and pre-releases are not used.

Server definitions are global. A repository may only propose a known server ID;
it may never define a command or activate a process. First enablement in each
workspace, and any later executable/argument/cwd/environment change, shows the
complete process definition and always asks before launch.

MCP child processes use shell false, explicit executable and argv, workspace cwd,
and a minimal environment; they never inherit any model-backend credentials.
Optional MCP credentials are references to namespaced keychain entries, not JSON
values.
The confirmation states that stdio roots and a scrubbed environment are not an OS
sandbox and the server still runs with the user's filesystem rights. Server
annotations are untrusted hints. Every result is size-limited,
terminal-sanitized, secret-scanned, and policy-classified.

Commands:

- mcp add, list, enable, disable, reconnect, logs, remove
- tools

Crash policy: one automatic process restart for a later call, then disable for the
run. A tool invocation is never automatically repeated. If the server may have
performed an effect before timeout or crash, that invocation ends indeterminate
and requires a new user decision. Timeout sends cancel then terminates. Sampling
and elicitation return unsupported. MCP failure never breaks built-in chat or
tools.

### 10.6 Read-only LSP manager

Orcode uses installed language servers only. Global configuration maps languages
to explicit executable and argv. A repository may suggest a mapping; the user
must enable it for each workspace. First enablement and every changed process
definition always ask and disclose that the server runs with user filesystem
rights. Launch uses shell false and the same scrubbed environment boundary as
MCP, without model-backend or unrelated credential variables.

Implement a small JSON-RPC stdio manager with Content-Length framing,
initialize/shutdown, cancellation, timeouts, document sync, and negotiated
position encoding.

Model capabilities:

- code_symbols
- code_definition
- code_references
- code_diagnostics
- code_hover when advertised

User commands:

- code status, symbols, definition, references, diagnostics, restart

Only file URIs inside the active workspace may be read or returned. Outside
results are counted and suppressed. Diagnostics are tied to document versions;
stale diagnostics are not displayed as current. Unsupported operations fall
back with an explicit label to text search, never as a silent equivalent.
No automatic server install and no LSP edit operation exists in 0.7.

### 10.7 Structured Git, worktrees, and GitHub PR

GitService uses direct executable plus argument arrays, never shell strings.
Machine data uses stable porcelain and NUL-delimited forms. Read operations set no
pager, no optional locks, no external diff, no textconv, and no fsmonitor. Worktree
operations use an empty hooks directory and block executable checkout/smudge
filters by default. Stage detects applicable clean/process filters and blocks them
until a direct user sees and always approves the exact programs and files. Commit
uses no hooks and no signing helper by default; each opt-in is a separate approval.
PR push rejects ext remotes, shows the selected remote and credential/helper path,
and remains a separate external-write approval. Config includes may be read for
this audit but never count as permission to execute a discovered helper.

Read-only model capabilities:

- git_status
- git_diff
- git_log

Direct user commands:

- git status, stage, unstage, commit, log
- worktree list, new, open, remove
- pr prepare, create, status, open

Worktrees live below ~/.orcode/worktrees/repository-id/branch-slug and use a
configurable default orcode/ branch prefix. No force flags are reachable.
Opening or removing requires an idle core. If a root, child, verifier, or job is
active, the UI can cancel-and-drain or abort the action; rebinding never races an
operation. A removable worktree must be clean, inactive, unlocked, on a branch
with one configured upstream, and have its local tip reachable from that upstream.
No upstream, detached HEAD, divergence, or multiple ambiguous remotes is treated
as unpushed and refused. Opening a worktree creates or selects its own chat and
rebinds workspace, LSP roots, MCP roots, journal, and agent without restarting
Orcode.

Before commit, show staged diff, files, and message. Hooks are skipped by
default because they execute repository code; running them is a separate
approval. Before stage, executable clean filters are detected and disclosed.

GitHub PR support uses an existing gh binary. Orcode stores no GitHub token.
Prepare is local; push and PR creation are separate external-write approvals.
Show remote, base/head, commits, diffstat, title, and body. No merge, force-push,
or automatic remote branch deletion exists in 0.7.

## 11. Unified error and recovery behavior

All subsystems return typed errors with:

- code,
- capability or task scope,
- short safe summary,
- redacted detail,
- retryable flag,
- concrete recovery command when available.

Shared codes include unavailable, login-required, usage-limit,
incompatible-backend, collaborator-failed, skill-invalid, approval-denied,
timeout, protocol-error, invalid-schema, process-exited, unsupported, conflict,
stale, indeterminate, recovery-required, unsafe-repository, budget-exhausted,
and interrupted.

The TUI always transitions out of spinning state and shows the affected
capability/task, duration, cause, and next action. Raw stack traces do not enter
model context. Redacted technical details remain locally inspectable.

Child, collaboration worker, model backend, MCP, LSP, Browser, SSH, skill load,
or verifier failure becomes a typed result for the root rather than crashing the
process. Required-child and verification outcomes use the finalization rules in
sections 9 and 10.3; optional failures remain visible warnings. Root cancellation
cascades. Child cancellation is local. A supervisor invariant failure cancels the
whole tree, preserves journal and logs, and reports interrupted.

## 12. Versioned storage and migration

Config gains schemaVersion. Chats advance from the current schema to v3 when
task origin, parent chat, workspace reference, execution mode, active skill IDs,
or collaboration recipe is needed. Permissions advance to an exact-subject
schema. Event logs use versioned envelopes. Provider configuration stores only
backend IDs, executable paths, supported-version observations, locally assigned
account aliases, keyed opaque account fingerprints, preferred role routes, and
last-known availability. It never persists a provider-supplied email, account
ID, organization name, or other profile field. Subscription credentials and
tokens are never part of Orcode storage, migrations, backups, logs, or chat
export.

Migration rules:

- Treat unversioned config as v0.
- Single-file rewrites validate complete output before atomic replacement.
- Multi-file imports use a persistent migration manifest with phase, source
  checksum, old-to-new chat ID map, destination paths, and completion marker.
  Copy into staging, validate the complete chat plus SDK state, run logs,
  checkpoints, journals, and task sidecars, then commit destinations and finally
  mark complete. Locks are not migrated. Every phase is idempotently resumable.
- Keep one protected backup of each rewritten source and record completed
  migrations. Backups are exact, potentially unredacted recovery artifacts.
- Never overwrite an unknown future version.
- Isolate one corrupt chat rather than blocking all chats.
- When ~/.routercode and ~/.orcode both exist, import legacy chats under new IDs,
  merge rules by stable fingerprint, keep new config authoritative, report
  conflicts, and use the persisted mapping for every sidecar. After validation,
  atomically rename the legacy directory into the one protected migration backup;
  do not leave a second unmanaged copy at ~/.routercode.
- Migration never requests a key or performs network work.

PrivateStore enforces mode 0700 directories and 0600 files on POSIX. On Windows it
creates a DACL for the current user SID and SYSTEM only. If that boundary cannot
be established, exact recovery artifacts are disabled with a visible warning;
they are never silently written to a broadly readable location. A migration that
requires an exact backup then aborts before any write and continues reading the
old schema without replacing it with defaults.

Default and maximum retention through 0.7 is:

- exact journals, SDK state, and checkpoints: 14 days, 20 terminal runs per chat,
  and 250 MiB globally, oldest first while never pruning an active run;
- redacted run logs: 30 days, 100 runs per chat, and 500 MiB globally;
- redacted MCP logs: seven days and 20 MiB per server;
- migration backups, including a renamed legacy home: one per source, 30 days,
  and 250 MiB globally;
- browser temporary artifacts: deleted on terminal outcome and on startup when
  older than 24 hours.

These ceilings may be configured downward, not upward, through 0.7. If one
required legacy backup exceeds its ceiling, migration aborts without writes and
asks the user to archive it manually. Chat deletion removes its transcript,
ID-mapped sidecars, exact artifacts, and mapped legacy entries inside the migration
backup after one confirmation; an empty backup is removed. Config backups are not
chat-owned. All visible versions are read from package.json.

## 13. Public distribution and release process

For every release:

1. Typecheck, tests, and build pass from a clean checkout.
2. npm audit has no high or critical production vulnerability.
3. npm pack output matches an explicit allowlist.
4. The tarball installs into a temporary prefix.
5. orcode and routercode version/help smoke tests pass.
6. CI covers macOS, Linux, and Windows on minimum Node 22; Linux also covers the
   current active LTS.
7. No tests, local logs, config, credentials, or private absolute paths ship.
8. package version, tag, banner, help, and changelog agree.
9. Real old-state fixtures migrate without data loss.
10. Release publication uses npm Trusted Publishing/OIDC and provenance after
    the npm account is configured; no long-lived npm token belongs in the repo.
11. Completion requires a fresh registry install, not only a successful action.

Publishing is an external-account action. Code and workflow preparation are in
scope; configuring the npm publisher identity and authorizing the first public
release require the repository owner's credentials and explicit final action.

## 16. Final design decisions

- Public and cross-platform, not Mac-only.
- Conversation-First Workbench, not a dense operations console.
- One process and one core, not services.
- Exact, visible authority and costs, not hidden autonomy.
- Direct child agents only, one writer, bounded parallelism.
- OpenRouter plus optional official ChatGPT/Codex and Claude managed-agent
  backends; no credential scraping or silent billing-realm fallback.
- Shared, source-qualified Codex, Claude, Orcode, and project skills are read
  directly, suggested locally, and activated only by the user.
- Cross, Scout, Debug, and Handoff are on-demand TaskGraph recipes over the same
  supervisor, not independent agent systems.
- MCP stdio tools only in 0.7.
- LSP navigation and diagnostics only in 0.7.
- Safe structured Git with user-driven mutations.
- Compatibility retained through 1.0.
- No release claim without green gates and a fresh registry installation.
