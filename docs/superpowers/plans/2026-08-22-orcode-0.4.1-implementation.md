# Orcode 0.4.1 Safe Foundation Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship Orcode 0.4.1 as the secure, correct, cross-platform release foundation required before the Conversation-First 0.5, orchestration 0.6, and extensibility 0.7 work begins.

**Architecture:** Keep the current CLI and agent structure, but replace divergent security paths with one canonical implementation at each boundary: one searcher, one redaction registry, exact approval subjects, one main-request builder, one conversation-history source, and one verification lifecycle. Storage operations become chat-scoped and retention-aware. Public packaging is generated and tested from the same command/version sources used at runtime.

**Tech Stack:** TypeScript 5.9, Node.js 22 ESM, `node:test`, `@openrouter/agent`, Zod, fast-glob, GitHub Actions, npm packaging.

**Spec:** `docs/superpowers/specs/2026-08-22-orcode-0.7-design.md`, especially sections 6, 7, 12, 13, and 14.

## Global Constraints

- Every behavior change starts with a failing test that demonstrates the user-visible or security contract.
- Never place real credentials, secret-shaped production values, account identifiers, or private user paths in fixtures or snapshots. Use deterministic synthetic values assembled in test code.
- Preserve unrelated user changes. Each task commits only its declared files or an explicitly recorded dependency discovered during implementation.
- The built-in workspace policy remains the authority for containment, protected paths, ignored files, symlink escape, and binary filtering.
- Exact recovery artifacts are not falsely described as redacted. They must use the PrivateStore boundary, bounded retention, and chat-owned deletion.
- A release claim requires fresh command output from all gates listed in Task 12. Registry publication remains an explicit owner action.
- Implementation agents are sequential because several tasks share `src/agent.ts`, `src/workspace.ts`, `src/commands.ts`, and `src/cli.ts`. Read-only review agents may run after each isolated commit.
